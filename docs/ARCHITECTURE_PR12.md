# PR12 — Journal comptable consultable, supervision technique, remise à zéro pré-ouverture, compatibilité matériel, identifiant de requête, tests de fumée

**Demande (15/09/2026, sélection n° 140, 150, 156, 167, 179 et 183 ; n° 168
livré en PR9) :** consulter le journal comptable ligne à ligne (n° 140) ;
une page de supervision technique (n° 150) ; repartir de zéro le jour de
l'ouverture (n° 156) ; le tableau du matériel compatible (n° 167) ; un
identifiant de requête visible côté caisse pour corréler avec le serveur
(n° 179) ; des tests de fumée automatiques après déploiement (n° 183).

Ce qui existe et qu'on **garde** : `AccountingService` (`build_journal_lines`,
exports par Z, FEC jour/mois, CSV mensuel), `RequestIdMiddleware`
(`X-Request-ID`, frontière 500 JSON avec `request_id`), `GET /api/health`
(version, `expected_db_revision`, `build_sha`), `jet/integrity`,
`fiscal/integrity`, `fiscal-closures/integrity`, `database/state`, la
sauvegarde applicative (PR5), `hardware/printer/status`, `scripts/deploy.sh`
(étapes 1/5 → 5/5), l'onglet Matériel, l'onglet Comptabilité. Aucune
migration dans cette PR (la révision attendue reste `0011`).

## 1. Contrats

| # | Fonction | Contrat |
|---|---|---|
| N1 | **Journal comptable consultable** | `GET /api/admin/accounting/journal?from=AAAA-MM-JJ&to=AAAA-MM-JJ&account=&z=` (JWT, période ≤ 366 jours, défaut mois courant) → `{period:{from,to}, lines:[{date, z_report_number, z_report_id, account_number, account_label, label, debit, credit, source: "export" \| "computed"}], totals:{debit, credit, balanced: bool}, accounts:[{account_number, account_label, debit, credit}], z_without_export:[report_number…]}`. Source des lignes : l'export comptable **enregistré** du Z quand il existe (`source="export"`, relu depuis son contenu immuable), sinon `build_journal_lines` à la volée (`source="computed"`, Z listé dans `z_without_export`). Montants en chaînes à deux décimales, tri date puis n° de Z puis n° de compte. Filtre `account` = préfixe de numéro de compte. 422 `invalid_date` / `period_too_long`. Aucune écriture, aucun JET (lecture). Front : onglet Comptabilité, carte **« Journal »** en tête : sélecteur de période (mois courant par défaut, ‹ ›), filtre compte, tableau (Date, Z, Compte, Libellé, Débit, Crédit), pied Totaux avec pastille « Équilibré » / « Déséquilibré » (rouge), avertissement listant les Z sans export enregistré avec renvoi vers la carte existante des exports, bouton **CSV du mois** (route existante `monthly-csv`). |
| N2 | **Supervision technique** (`services/monitoring.py`, `GET /api/admin/monitoring`) | Réponse `{generated_at, app:{version, build_sha, build_date, environment, expected_db_revision, current_db_revision, db_revision_ok, uptime_seconds}, database:{ok, latency_ms, size_bytes, tables_count}, backups:{last:{created_at, status, size_bytes} \| null, nightly_enabled, dir_free_bytes, stale: bool (dernier succès > 36 h)}, jobs:[{name, cron, next_run_at, last_run:{at, status: "ok" \| "failed", detail} \| null}] (lus depuis le planificateur APScheduler + derniers événements JET `system.job_*`), integrity:{jet:{valid, count, checked_at}, fiscal:{valid, checked}, closures:{valid, checked}} (calculées à la demande de `?check=1`, sinon dernier résultat en cache mémoire ≤ 10 min, `null` si jamais calculé), external:{sumup:{configured, reader_configured, last_ping:{ready, at} \| null}, brevo:{configured}, openweather:{configured, cache_age_seconds \| null}}, printer:{mode, online \| null, latency_ms \| null}, queues:{failed_payments_pending, sumup_exchange_errors_24h, clients_deletion_due}, recent_errors:[{at, request_id, method, path, status, error_type}] (tampon mémoire circulaire des 50 dernières réponses 500 alimenté par `RequestIdMiddleware`, jamais de corps ni de PII), status: "ok" \| "warning" \| "critical"}` — `critical` si base KO, révision de base différente ou intégrité invalide ; `warning` si sauvegarde périmée, TPE non prêt, imprimante hors ligne, erreurs 500 dans l'heure, ou file de paiements non vide. Aucun secret. `POST /api/admin/monitoring/check` → recalcule les trois intégrités et renvoie la réponse complète (JET `fiscal.integrity_checked` existant). Front : nouvel onglet **« Supervision »** (`/admin?tab=monitoring`, entrée Administration après Sauvegardes, icône activité) : bandeau d'état global coloré, cartes Application / Base / Sauvegardes / Tâches planifiées / Intégrité (bouton **Vérifier maintenant**) / Services externes / Imprimante / Files / Dernières erreurs (identifiant de requête copiable). Rafraîchissement toutes les 60 s tant que l'onglet est visible. |
| N3 | **Remise à zéro pré-ouverture** (`scripts/go_live_reset.py`) | Script à lancer dans le conteneur API (`docker exec -it fripco-api python scripts/go_live_reset.py --dry-run` puis `--confirm`), connexion par `MIGRATION_DATABASE_URL` (rôle propriétaire, seul à pouvoir tronquer). **Conserve** : `users`, `app_settings`, `cashiers`, `database_backups` (lignes et fichiers). **Vide** (`TRUNCATE … RESTART IDENTITY CASCADE`, en une seule transaction) : `transactions`, `transaction_items`, `payments`, `receipts`, `payment_attempts`, `failed_payments`, `sumup_exchanges`, `cash_drawers`, `cash_movements`, `z_reports`, `accounting_exports`, `fiscal_closures`, `invoices`, `journal_events`, `clients`, `consents`, `communications`, `cahier_days` — la liste est **explicite** dans le script (jamais « toutes les tables sauf ») et vérifiée contre `information_schema` : une table inconnue du script fait échouer le dry-run (« table non classée »), pour qu'une future migration ne soit jamais vidée ou conservée par accident. Ordre : (1) refus si le réglage `system.go_live_done_at` est posé (sauf `--force`, qui exige de retaper le nom de la boutique) ; (2) sauvegarde applicative **manuelle** via `database_backup.run_backup(trigger="manual")` — échec de sauvegarde = arrêt ; (3) comptages avant ; (4) TRUNCATE ; (5) réinitialisation des séquences (`transaction_number`, `report_number` repartent à 1 ; la chaîne fiscale redémarre sur le genesis) ; (6) premier événement du nouveau JET : `system.go_live_reset` `{at, by: "script", previous_counts:{…}, backup_id}` ; (7) réglage `system.go_live_done_at`. `--dry-run` n'écrit rien et affiche le plan (tables, comptages, sauvegarde qui serait faite). Les triggers d'immutabilité ne sont **jamais** désactivés (`TRUNCATE` ne déclenche pas les triggers de ligne) ; si une erreur survient, tout est annulé (ROLLBACK). Test d'intégration : sur une base peuplée, dry-run sans effet, confirm → tables vides, `users`/`cashiers`/`app_settings` intacts, séquence à 1, premier JET `system.go_live_reset` valide (`verify_chain`), second lancement refusé. `docs/DEPLOIEMENT.md` : procédure « Jour de l'ouverture ». `docs/ATTESTATION_NF525.md` : une phrase — la remise à zéro est une opération documentée d'avant-ouverture, tracée comme premier événement du journal, jamais utilisable après (verrou `go_live_done_at`) ; §6 intact. |
| N4 | **Tableau de compatibilité matériel** | `GET /api/hardware/compatibility` (JWT) → `{items:[{category, model, connection, status: "tested" \| "recommended" \| "not_supported", notes}]}`, liste statique dans le code : tablette Android + Chrome (testé), imprimante MUNBYN 047P ESC/POS 80 mm (réseau TCP 9100 : testé ; USB-OTG WebUSB : testé), tiroir Safescan SD-4141 via l'imprimante (testé), TPE SumUp Solo (testé, push direct si `reader_id`), iPad / Safari (non supporté : pas de WebUSB ni d'installation Chrome), douchette USB HID (recommandé, non nécessaire sans catalogue). Onglet Matériel : carte **« Matériel compatible »** (tableau, pastilles de statut, notes). |
| N5 | **Identifiant de requête côté caisse** | `lib/api.ts` : chaque appel envoie un `X-Request-ID` généré (`crypto.randomUUID()`, 16 premiers caractères) et `ApiError` porte `requestId` (en-tête de réponse `X-Request-ID` ou champ `request_id` du corps). Les bandeaux d'erreur de la caisse (`PaymentStatusBanner`, écran de succès/erreur de vente, mouvement, clôture) et le composant d'erreur générique de l'administration affichent, pour toute erreur **5xx ou réseau**, une ligne discrète « Référence : `abcd1234efgh5678` » avec bouton copier ; jamais pour une 4xx métier (le message suffit). Backend : `RequestIdMiddleware` renvoie l'en-tête sur **toutes** les réponses (vérifier, y compris les erreurs levées par les handlers `PosServiceError`) et alimente le tampon `recent_errors` de N2. Guide vendeur : « En cas d'erreur, note la référence ». |
| N6 | **Tests de fumée post-déploiement** (`scripts/smoke_prod.sh`) | `scripts/smoke_prod.sh [URL]` (défaut `https://app.lloomi.fr`), bash + `curl` + `python3` (présents sur le VPS), lecture seule : (1) `GET /api/health` 200, `app == fripco-street-api`, `expected_db_revision` égal à la tête Alembic du dépôt (`ls apps/api/alembic/versions` → dernier préfixe) et `build_sha` égal au commit déployé (`git rev-parse --short HEAD`) ; (2) `GET /` 200 et contient `Frip & Co Street` ; (3) `GET /login` 200 ; (4) `GET /manifest.webmanifest` 200 JSON valide ; (5) `GET /sw.js` 200 ; (6) `GET /api/openapi.json` 200 ; (7) certificat TLS valide plus de 14 jours ; (8) `/api/health` en moins de 2 s ; (9) `GET /api/admin/monitoring` sans jeton → 401 (l'admin n'est pas public). Sortie : une ligne par contrôle `[OK]`/`[KO]`, code de retour 1 dès un `[KO]`. `scripts/deploy.sh` : nouvelle étape **6/6 « Tests de fumée »** qui lance le script après le message de fin ; un `[KO]` affiche `Rollback : ./scripts/deploy.sh --rollback` et sort en 1 (le déploiement a déjà eu lieu : on ne le défait pas automatiquement). `docs/DEPLOIEMENT.md` : section correspondante. |
| N7 | **Docs et version** | `docs/MANUEL_MANAGER.md` : « Journal comptable », « Supervision », « Matériel compatible ». `GUIDE_VENDEUR.md` : référence d'erreur. `README.md` ligne PR12. `APP_VERSION` → `0.13.0` (révision de base inchangée `0011`, `tests/test_health.py` inchangé sauf version si testée). |

# PR8 — Vendeuses par code PIN (relève) et facture B2B

**Demande (15/09/2026, sélection n° 29 et 30) :** identifier la vendeuse qui
encaisse, permettre la relève en cours de journée, éditer une facture pour
un client professionnel (raison sociale + SIRET). Le compte manager unique
(connexion mot de passe) reste le seul compte de l'application : les
vendeuses ne sont pas des utilisateurs, ce sont des **identités de caisse**
protégées par un code PIN à 4 chiffres.

## 1. Contrats

| # | Fonction | Contrat |
|---|---|---|
| J1 | **Table `cashiers`** (migration `0008_cashiers_invoices`) | `id` uuid, `display_name` varchar(60) non nul, unique insensible à la casse, `pin_hash` varchar(100) (bcrypt via `core/security.hash_password`), `active` bool défaut true, `created_at`, `updated_at`, `deactivated_at` nullable. Jamais supprimée (désactivation seulement : les ventes y font référence). Colonne `cashier_id` uuid **nullable** FK sur `transactions`, `cash_movements`, `z_reports` (`opened_by_cashier_id` et `closed_by_cashier_id` sur `cash_drawers`). **Hors signature** (comme `client_id`) mais posée à l'INSERT et protégée par les triggers d'immutabilité existants : ajouter `cashier_id` à la liste des colonnes gelées des triggers de `transactions` et `cash_movements` (réécriture des fonctions de protection dans la migration, réversible). |
| J2 | **Identification en caisse** | Réglage `pos.cashier_required` (bool, défaut **false**, dans les réglages `pos` ou `shop` existants) : quand il est vrai, aucune vente ni mouvement n'est possible sans vendeuse identifiée (422 `cashier_required`). `cash_drawers.current_cashier_id` uuid nullable, **mutable** (état courant, pas fiscal). Routes (JWT) : `GET /api/pos/cashiers` (actives, `{cashiers:[{id, display_name, has_pin}]}`), `POST /api/pos/cashiers/identify` `{cashier_id, pin}` → 200 `{cashier:{id, display_name}}` ; 401 `invalid_pin` ; **rate-limit 5 essais / 5 min par vendeuse et par IP** (réutiliser `core/rate_limit.py`, JET `cashier.pin_rejected` sans PIN) ; `POST /api/pos/cashiers/release` → 200 (relève : retire l'identité courante). Chaque vente, annulation et mouvement porte `cashier_id = current_cashier_id` du tiroir au moment de l'opération. JET `cashier.identified` `{cashier_id}` et `cashier.released` `{cashier_id}`. `GET /api/pos/drawer/current` expose `current_cashier: {id, display_name} \| null`. Le ticket porte `Vendeuse : Prénom` (display_name) sous la ligne Date (même mécanisme de rendu que la ligne Client, inséré à l'émission dans le texte stocké). Le rapport Z liste la ventilation des ventes par vendeuse (`by_cashier: [{cashier_id, display_name, sales_count, sales_total}]`) dans le JSON existant du Z et sur son PDF. |
| J3 | **Administration des vendeuses** | Entrée **Vendeuses** dans le groupe Commerce de la barre latérale → `/admin?tab=cashiers`. Onglet : liste (nom, PIN défini oui/non, active), ajouter (nom + PIN 4 chiffres saisi deux fois), changer le PIN, désactiver / réactiver, et la case « Identification obligatoire en caisse ». Routes admin (JWT) : `GET/POST /api/admin/cashiers`, `PUT /api/admin/cashiers/{id}` (nom, active), `PUT /api/admin/cashiers/{id}/pin`. PIN : exactement 4 chiffres, refus des suites triviales `0000`, `1234`, `1111`… (liste courte), 422 `weak_pin`. JET `cashier.created` / `cashier.updated` / `cashier.pin_changed` (sans PIN ni hash). |
| J4 | **Front caisse** | Dans `PosTopBar` : pastille de la vendeuse courante (« Vendeuse : Léa ») avec bouton **Relève** ; si personne : bouton **S'identifier** (accentué). Écran plein écran `CashierIdentifyScreen` : cartes des vendeuses actives, puis pavé PIN 4 chiffres (points masqués), erreur « Code incorrect » et compte à rebours en cas de blocage. À l'ouverture de caisse, si `cashier_required`, l'identification est demandée avant d'ouvrir. Après la relève, le panier en cours est conservé. Mode démo aligné. |
| J5 | **Facture B2B** | Table `invoices` (migration 0008) : `id`, `transaction_id` unique FK, `invoice_number` varchar(20) unique séquentiel **`F-AAAA-NNNN`** (compteur par année, attribué sous le même verrou fiscal que les ventes), `company_name` (120), `siret` (14 chiffres, validation Luhn), `vat_number` nullable (FR + 11), `address_line1`, `address_line2` nullable, `postal_code`, `city`, `issued_at`, `seller_snapshot` (JSONB : nom, adresse, téléphone, e-mail, SIRET et n° TVA de la boutique **figés à l'émission**, recopiés sur l'avoir ; le PDF se rend uniquement à partir de ce bloc, jamais des réglages courants, sinon un changement de réglage casserait la reproductibilité), `pdf_sha256`. **Immuable** (trigger UPDATE/DELETE refusés, sauf `pdf_sha256` posé une fois). Une facture ne peut être émise que sur une **vente** non annulée, une seule fois (409 `invoice_exists`) ; une vente facturée peut être annulée : l'annulation génère un **avoir** `A-AAAA-NNNN` (même table, `kind` enum `invoice`/`credit_note`, `original_invoice_id`) automatiquement. Routes (JWT) : `POST /api/pos/transactions/{id}/invoice` `{company_name, siret, vat_number?, address_line1, address_line2?, postal_code, city}` → 201 `{invoice}` ; `GET /api/pos/transactions/{id}/invoice` ; `GET /api/pos/invoices/{id}/pdf` (reportlab, **déterministe** comme le PDF du Z : en-tête boutique avec SIRET et n° TVA de `shop`, client, lignes HT / TVA / TTC, aucune mention de régime particulière (ventes de biens en régime normal, TVA exigible à la livraison), pénalités de retard et indemnité forfaitaire de 40 € légales, n° de facture, date, n° de ticket associé) ; `GET /api/admin/invoices?year=` liste. JET `invoice.issued` `{invoice_id, transaction_id, invoice_number}`, `export.downloaded` sur le PDF. Le ticket de la vente facturée porte `Facture : F-2026-0001`. Le client B2B **n'est pas** une fiche client (pas de mélange avec les personnes physiques) ; les données de facture sont conservées 10 ans, exclues de l'anonymisation RGPD, incluses dans l'archive de clôture et dans l'export fiscal. |
| J6 | **Front facture** | Sur l'écran de succès d'une vente et dans le détail d'un ticket du jour : bouton **« Facture pro »** → formulaire (raison sociale, SIRET avec validation, n° TVA, adresse) → « Émettre la facture » → n° affiché + **Télécharger le PDF** (via `lib/download.ts`). Admin → Comptabilité : carte « Factures » (liste par année, PDF). Mode démo aligné. |
| J7 | **Docs et version** | `GUIDE_VENDEUR.md` : « S'identifier et faire la relève », « Facture pour un professionnel ». `PROCEDURE_CLOTURE.md` : ventilation par vendeuse sur le Z. `ATTESTATION_NF525.md` : factures et avoirs numérotés, immuables, hors signature des ventes mais chaînés par le JET (une phrase par point, §6 intact). `README.md` ligne PR8. `APP_VERSION` → `0.9.0`, `EXPECTED_DB_REVISION` → `"0008"`. |

## 2. Hors périmètre
Comptes utilisateurs multiples et rôles (n° 135, non retenu), facture sur une annulation partielle (l'avoir couvre l'annulation totale ; l'annulation partielle d'une vente facturée est refusée 409 `invoiced_partial_refund`), envoi de la facture par e-mail (le PDF se télécharge).

## 3. Tests attendus
- Migration 0008 aller-retour ; triggers gèlent `cashier_id` sur `transactions` / `cash_movements`.
- PIN : hash bcrypt, identification OK / KO, rate-limit après 5 échecs (429), `weak_pin`, désactivation empêche l'identification, JET sans PIN.
- Ventes : `cashier_id` posé depuis le tiroir ; `cashier_required` → 422 ; relève puis vente → nouvelle vendeuse ; hash de la vente identique avec ou sans vendeuse (hors signature) ; Z : `by_cashier` exact sur le jeu d'essai.
- Factures : numérotation séquentielle par année sous verrou (deux émissions concurrentes → numéros distincts), SIRET invalide 422, deuxième facture 409, annulation → avoir `A-…` lié, PDF déterministe (même sha256 à deux appels), archive de clôture contient les factures, anonymisation d'un client ne touche pas les factures.
- Front : lint, tsc, build ; parcours réel (validateur).
- Isolation : `tests/test_isolation.py` vert.
